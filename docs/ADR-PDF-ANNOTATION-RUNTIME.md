# ADR: PDF annotation runtime boundary

- Status: Accepted for the public graph-first hackathon slice
- Date: 2026-08-30
- Decision owners: PaperPilot project owner and implementation agent
- Related requirements: `docs/hackathon-build/scope.md`, `prd.md`, and `spec.md`

## Context

PaperPilot must let a reader mark exact text, arbitrary page regions, whole figures, and figure regions while the PDF remains the central reading surface. Those marks must support WebMCP reads and reversible agent commands, remain registered during zoom and reflow, reopen their exact evidence, work through an accessible nonvisual representation, and preserve future compatibility with annotations embedded into PDF bytes.

The project owner proposed [`highkite/pdfAnnotate`](https://github.com/highkite/pdfAnnotate), published on npm as `annotpdf`, as an annotation foundation. The evaluated repository revision was `b5e5bc2a4947d604610d15d78f47289074a0f2b7`; the evaluated npm version was `1.0.15`; both use the MIT license.

The evaluated library is a low-level PDF parser/writer for adding annotation objects to PDF bytes. It is not the interactive viewer, selectable text layer, overlay renderer, accessibility tree, undo history, knowledge-graph model, or WebMCP authority boundary PaperPilot needs. Its value appears when an application intentionally writes annotations into a downloadable or otherwise mutated PDF.

The approved hackathon scope explicitly prevents PDF export and keeps the reading experience inside PaperPilot. Shipping a byte writer now would add parsing, serialization, compatibility, security, and destructive-update risk without satisfying the visible interaction requirements.

## Decision

PaperPilot will use:

1. PDF.js to render pages and provide the positioned selectable text layer.
2. PaperPilot-owned DOM/SVG layers for visible highlights, regions, labels, focus states, and graph-linked annotations.
3. A PaperPilot-owned, versioned PDF-space anchor contract for points, rectangles, and quadrilaterals.
4. The trusted graph/annotation command reducer for validation, provenance, atomic application, inverse patches, Undo/Redo, and reversible tombstones.
5. An accessible DOM representation for every annotation independent of the visual overlay.

`annotpdf` will not be installed, imported, vendored, or called by the public release. No application feature will mutate or export PDF bytes in this scope.

## Geometry interoperability contract

Every visual anchor must be document-qualified and include enough information to reproduce or translate the marked region:

- document ID and immutable PDF digest;
- page index;
- PDF-space rectangle or quadrilateral coordinates in a documented coordinate system;
- page crop/media box and rotation context;
- renderer/anchor schema version;
- optional exact-text offsets and quote digest;
- annotation kind, authority, graph linkage, and provenance receipt;
- lifecycle state, including reversible tombstone state.

Viewport coordinates are ephemeral. They are converted to PDF space at the interaction boundary and regenerated from PDF space for each render. A future exporter may translate this contract into a selected PDF-writer library without changing WebMCP schemas, graph IDs, or stored provenance.

## Consequences

Positive consequences:

- The central Reader, annotations, graph navigation, accessibility, and Undo/Redo can be built without mutating source bytes.
- The release avoids claiming annotation embedding or export it does not provide.
- The source PDF remains immutable, simplifying digest binding and provenance.
- A future byte writer remains replaceable because PaperPilot owns the geometry and command contracts.

Tradeoffs:

- Annotations exist only inside PaperPilot in this release.
- Other PDF viewers cannot see PaperPilot annotations.
- A future export feature will need a separate threat model, compatibility matrix, explicit user action, output provenance, and verification that generated bytes preserve the source and expected annotation geometry.

## Reconsideration trigger

Reconsider the runtime dependency only after the owner approves PDF export or embedded-annotation persistence. That decision must compare current PDF writers, validate arbitrary-PDF compatibility and security, define immutable-original versus derived-output custody, and add round-trip visual verification. The earlier evaluation is not a permanent endorsement of one library.

## Verification

- The dependency manifest and built bundle contain no `annotpdf` import.
- The UI exposes no PDF export or download-with-annotations action.
- Geometry round-trip tests cover zoom, resize, page rotation, and at least two unrelated PDFs.
- The same stored anchor reopens the exact marked region after refresh.
- WebMCP commands cannot supply raw PDF object mutations or arbitrary byte-writer parameters.
