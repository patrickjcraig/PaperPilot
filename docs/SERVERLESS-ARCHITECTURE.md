# PaperPilot Serverless Architecture

**Status:** Approved and required

**Decision date:** 2026-08-30

**Supabase project:** `avmcmmayvnjxrhrmgsdx`
**Scope:** Tuesday WebMCP hackathon candidate and its production-shaped deployment

## Decision

PaperPilot is serverless. Its release may not depend on a VPS, Docker Compose
host, continuously running worker, persistent ClamAV daemon, shared local
volume, production-local filesystem, or local database.

The approved runtime is:

```text
ChatGPT built-in browser / ordinary browser
  |
  | HTTPS UI, auth, metadata, WebMCP callbacks
  v
Vercel Next.js Functions
  |                         \
  | bounded SQL              \ start/signal durable PDF job
  v                           v
Supabase Postgres          Vercel Workflow
  ^                           |
  | durable status/receipt    | IDs/digests only
  |                           v
  |                      Vercel Sandbox
  |                      persistent: false
  |                      qpdf + ClamAV + Poppler
  |                           |
  +---------------------------+

Browser -- exact signed transfer -----------------> private Supabase Storage
Sandbox -- exact host/path/method + placeholder --> Vercel Sandbox firewall
                                                     | scoped credential
                                                     | transform
                                                     v
                                                   private Supabase Storage
```

Supabase is the sole durable data plane:

- PostgreSQL owns users, tenants, jobs, leases, admitted document identity,
  exact extracted text, source sets, proposals, activity, and human decisions.
- Private Storage owns original PDFs and retained visual/processing artifacts.
- Vercel Workflow owns orchestration only. Its trace is not provenance or
  user-visible job authority.
- Vercel Sandbox owns no durable state. It is a disposable execution boundary
  for one PDF attempt.

## Why PDF bytes bypass Functions

PaperPilot's documented PDF limit is larger than Vercel Functions' request and
response body limit. Proxying uploads or Reader PDFs through a Route Handler
would therefore make arbitrary admitted PDFs fail for platform reasons and
would buffer hostile input in the control plane.

The application instead uses a capability protocol:

1. An authenticated Function reserves an attempt-specific random object key,
   expected byte count, expected SHA-256, quota, actor, workspace, asset, and
   expiry in PostgreSQL.
2. It returns a signed upload capability for that one new key. Overwrite is
   disabled. Supabase currently fixes the provider capability lifetime at
   approximately two hours; PaperPilot may expose a shorter usable lease but
   cannot claim that the provider token was revoked at that earlier deadline.
3. The browser uploads directly to the private bucket.
4. A finalize command heads the exact object, fences idempotent replay, and
   starts Workflow. Successful transfer is not validation admission.
5. A Sandbox rechecks byte count and SHA-256 before qpdf/ClamAV/Poppler run.
6. An authorized Reader request returns a short-lived capability for the
   admitted write-once object path. PDF.js independently verifies the admitted
   byte count and SHA-256 before granting rendered-page authority.

Signed URLs are bearer capabilities. PaperPilot never logs them, stores them as
durable provenance, returns a bucket-wide capability, or sends the Supabase
service-role key to a browser, Workflow argument, or Sandbox.

### Supabase signed-capability limits

The pinned public Supabase Storage SDK does not make a signed upload into
content admission. Its upload token binds the bucket/key, create-versus-upsert
mode, scope, and provider expiry; it does **not** bind PaperPilot's expected
byte count, MIME type, or SHA-256. A successful upload plus `info()` therefore
establishes only a quarantined provider object. The Function must compare the
exact key, bucket, size, declared PDF MIME, and nonempty provider version, but
only the disposable Sandbox's full snapshot, SHA-256 calculation, and PDF
validation may create admitted authority.

The same SDK's `createSignedUrl(path, ttl)` is current-path based and does not
expose the Storage service's provider-version parameter. PaperPilot does not
call that result generation-pinned. Release correctness instead requires:

- unique attempt-specific keys generated by PaperPilot and never recycled;
- create-only upload (`upsert: false`);
- cleanup delayed until the two-hour provider write window plus safety margin;
- a bounded complete snapshot with matching provider metadata before and after
  staging when the Sandbox uses the supported SDK-only path; and
- byte-count and SHA-256 verification of that immutable snapshot before any
  parser or PDF.js rendering receives authority.

An optional provider-version REST adapter may be added only behind a live
managed-project integration probe. It is not inferred from, or smuggled
through, an unsupported SDK option.

The browser and Sandbox use different credential protocols. Browser upload and
Reader download use short-lived exact-object signed capabilities because those
transfers do not enter Workflow. A Sandbox command must never receive a signed
URL, storage JWT, service-role key, or credential-bearing environment variable:
Sandbox SDK calls are durable Workflow steps and their arguments are observable.

Instead, a server-only **storage-egress binder** loads a short-lived,
attempt-scoped Storage JWT inside one explicit server step and installs it as a
Vercel Sandbox firewall request transform. The rule is bound to the configured
project host, exact normalized object path, one method set, expected placeholder
header, Vercel project/team, returned native Sandbox name, and current fenced job
attempt. The binder returns only a closed success/failure code. The guest sends
the non-authorizing path and placeholder header; Vercel injects the scoped
credential outside the guest process. After staging or publication, the
lifecycle overwrites the rule with `deny-all`.

This binder and its Supabase Storage RLS/JWT policy are a mandatory Gate 0
implementation and trace-verification item. Until that trace proves no
credential appears in Workflow inputs, outputs, command arguments, logs, or
serialized Sandbox state, the live Storage/Sandbox path remains unavailable.

## PDF workflow

Each finalized upload starts one idempotent Workflow run using only bounded
identifiers. The Workflow performs these durable phases:

1. **Prepare:** lock/fence the Supabase job attempt; verify it is current; record
   the Workflow run ID; return only bounded IDs, digests, limits, and policy
   identities—never a signed URL or storage credential.
2. **Create:** call `Sandbox.create` with `persistent: false`, bounded timeout
   and resources, a digest-pinned PDF-tools image, and `deny-all` networking.
   Keep Vercel's native Workflow-serializable `Sandbox` value and bind its name
   to `jobAttemptId`; do not wrap it in a plain function-valued object.
3. **Stage:** the server-only binder installs one exact GET/HEAD firewall
   transform, then the Sandbox obtains exactly one reserved PDF using a
   non-authorizing path and placeholder header. Recheck size and SHA-256 before
   any document parser sees it.
4. **Air-gap and validate:** switch to deny-all egress for untrusted parsing;
   run qpdf structural checks and ClamAV with a recorded signature identity.
5. **Extract:** only an accepted PDF reaches Poppler. Produce bounded canonical
   text/manifest artifacts and a closed receipt; never emit raw paths or command
   output as product data.
6. **Publish:** install a separate exact output-only firewall transform, publish
   bounded artifacts, then restore deny-all; do not pass artifact bytes or the
   injected credential through Workflow state.
7. **Commit:** atomically reject stale lease/object/attempt/policy/toolchain
   results, admit the valid manifest, and persist the receipt in Supabase.
8. **Destroy/reconcile:** attempt stop in `finally` for ordinary success,
   rejection, retryable failure, timeout surfaced to the run, abort, and
   exception. Persist cleanup state. A scheduled idempotent reconciler lists
   PaperPilot-tagged Sandboxes and stops any cancelled, expired, superseded, or
   terminal attempt whose stop was not confirmed. The bounded Sandbox timeout
   is the last backstop; external Workflow cancellation is never assumed to run
   application `finally`.

A retry creates a new `jobAttemptId` and a different Sandbox. Late receipts from
an earlier attempt cannot mutate the current document.

## Serverless database profiles

PaperPilot keeps two non-interchangeable database authorities:

| Use | Connection | Required behavior |
|---|---|---|
| Vercel Function and Workflow steps | Exact dashboard-issued Supavisor transaction-mode endpoint on port `6543` | Project-scoped runtime role; low connection ceiling; prepared statements and session-state assumptions disabled |
| Reviewed migration/release job | Exact direct Supabase database endpoint on port `5432` | Separate migration authority; never present in browser or Sandbox; no normal request traffic |

Both profiles must prove project `avmcmmayvnjxrhrmgsdx`, TLS verification,
database `postgres`, expected role identity, and environment purpose before a
socket opens. The runtime profile must reject the production migration role,
and the migration profile must reject the runtime role. Neither accepts a
loopback, generic, or alternate-project destination.

## Provider-neutral boundaries

Domain services depend on two narrow contracts:

- `PrivateObjectControlPlane` reserves exact keys, issues upload/read
  capabilities, heads exact objects, and deletes or tombstones through an
  idempotent fenced operation. It exposes no PDF byte-reading method and its
  metadata result is quarantine evidence, not admitted content identity.
- `PinnedObjectStore` belongs to the Sandbox staging boundary. It obtains one
  bounded immutable snapshot and verifies byte count/SHA-256 before exposing
  that snapshot to any validator, extractor, or Reader authority.
- `PdfSandboxRunner` accepts one immutable input identity plus attempt/policy
  limits and returns one bounded receipt. The contract requires
  `persistent: false`, exact input verification, policy/toolchain identity,
  termination evidence, and no secret/content telemetry.

Supabase Storage and Vercel Sandbox are adapters behind those contracts. The
existing local-quarantine and one-shot validator/extractor logic may serve as
test/porting references, but no production code may silently select them.

The Workflow-facing Vercel adapter must retain the SDK's native `Sandbox`
instance so its official custom serializer survives durable step replay. A
plain object containing bound methods is forbidden at this boundary.

## Security and provenance invariants

- Exact text remains the admitted Poppler reconstruction; PDF.js text does not
  become exact authority.
- A rendered figure/region remains exact retained client-produced bytes bound
  to document, page, geometry, renderer recipe, and digest.
- The browser agent reads only a user-confirmed immutable source set.
- No WebMCP tool saves, discards, approves, verifies, broadens source scope, or
  retrieves semantically similar private content.
- The Sandbox has no database credential, no Supabase service-role credential,
  no unrelated object capability, and no cross-attempt state.
- PDF text, image bytes, signed capabilities, injected Storage JWTs, secrets,
  and raw command output are absent from logs and Workflow state. Opaque object
  identity may appear only where a durable step requires it and is never a
  credential by itself.
- Vercel `/tmp` is scratch space only and never durable authority.
- Provider quota exhaustion yields an explicit unavailable/retry state. It
  never activates a VPS, local database, or filesystem fallback.

## Vector retrieval decision

No vector database participates in the exact-selection mentor path. The user
has already selected the evidence, so semantic retrieval would weaken the
sharing preview and deterministic source/proposal binding.

If PaperPilot later adds optional within-paper or library discovery, it starts
with hybrid PostgreSQL full-text search plus `pgvector` in the same Supabase
database. Candidates must be shown to the user and pass the ordinary sharing
preview/source-freeze path before WebMCP can read them. A separate vector
service requires measured scale or latency evidence and a new architecture
decision.

## Verification gates

Every-commit checks **must** use provider-neutral fakes plus the official
Sandbox mock to prove native SDK launch arguments, serialization-compatible
values, idempotency, stale-result rejection, air-gap transitions, and ordinary
teardown paths without consuming cloud quota. As of the first architecture
cycle, the official mock proves only native safe launch construction; the
Workflow/job replay, binder, stale-result, and reconciliation suites remain
required before Gate 0 can pass.

A Vercel Preview release must additionally prove:

- signed-in reserve → direct private upload → finalize;
- the Function never receives the PDF body;
- exact Supabase project/runtime profile and private bucket policy;
- Workflow dispatch/resume with durable status in Supabase;
- one real Sandbox per attempt with `persistent: false`;
- an initially deny-all Sandbox and an exact host/path/method credential
  transform installed without any credential in durable Workflow observability;
- distinct Sandbox IDs for retries and no cross-document state;
- qpdf/ClamAV/Poppler versions and signature/policy identity;
- size/SHA-256 agreement before processing and before commit;
- confirmed stop after ordinary success, rejection, timeout, abort, and
  exception plus reconciler cleanup after external cancellation/termination;
- no database/service-role secret or PDF content in Sandbox/Workflow logs;
- admitted write-once Reader download plus client byte-count/digest
  verification; and
- two consecutive previously unseen PDFs through first-page render, with one
  born-digital file reaching exact text.

The final evidence bundle records the Vercel deployment URL/ID, commit,
Supabase project ref, Workflow run IDs, Sandbox IDs, input/output digests,
policy/toolchain identities, sanitized activity, and pass/fail gates. It does
not contain private source bytes, signed URLs, credentials, cookies, storage
paths, or hidden model reasoning.

## Free-tier operating envelope

The hackathon demo is deliberately bounded:

- pass only IDs/digests through Workflow, never PDFs;
- use `persistent: false` so disposable runs do not create automatic snapshots;
- cap concurrent PDF jobs below the account's Sandbox quota;
- use one prebuilt digest-pinned image rather than installing tools per upload;
- persist status in Supabase because Workflow trace retention is not product
  retention; and
- expose clear quota/backoff errors instead of unbounded retries.

PaperPilot must be upgraded from personal/non-commercial Hobby use before it is
operated as a commercial or broadly available production service.

## Implementation order

1. Install and wire stable Workflow/Sandbox SDKs and provider contracts with
   credential-free lifecycle tests.
2. Add the exact Supavisor runtime profile and separate direct migration path.
3. Add the private bucket plus browser reserve/finalize signed transfer adapter,
   scoped Sandbox Storage JWT policy, and exact firewall-transform binder.
4. Build and pin the PDF-tools image; implement the one-attempt native-Sandbox
   runner and orphan reconciler.
5. Wrap validation/extraction one-shot behavior in Workflow and persist bounded
   receipts/job state in Supabase.
6. Replace the Reader body proxy with exact-generation signed download.
7. Replace Compose preflight with Preview/Supabase/Workflow/Sandbox checks.
8. Deploy the Preview, run the real PDF matrix, then execute the named-client
   WebMCP truth spike.
